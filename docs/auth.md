# معماری احراز هویت — Persboy (بخشی از Phase 3)

> وضعیت: **پیاده‌سازی‌شده و تست واحد شده.** تست‌های یکپارچه (DB واقعی) نوشته شده‌اند
> ولی در sandbox فعلی اجرا نشدند (دلیل: پایین را ببینید). باید در dev/CI واقعی تأیید شوند.

منبع تصمیمات: تأیید صریح کاربر روی پیشنهاد ارائه‌شده (مبتنی‌بر ارزیابی معماری Legacy —
`fruit-veg-store-backend`، نه کپی کورکورانه) + دو مورد اضافه‌ی تأییدشده: بازیابی رمز ادمین از
طریق OTP، و مدیریت نشست‌ها (لیست/ابطال دستگاه).

## ۱. دو مسیر ورود جدا

| نقش | مکانیزم |
|---|---|
| customer / courier | فقط OTP پیامکی — بدون رمز عبور |
| admin / master_admin | فقط رمز عبور — مسیر کاملاً جدا (`/api/v1/auth/login/password`) |

هیچ فرم ثبت‌نام جداگانه‌ای وجود ندارد: اولین بار که یک شماره با OTP تأیید شود، حساب
`customer` ساخته می‌شود. **اولین کاربری که در کل تاریخچه‌ی سیستم این کار را انجام دهد،
به‌طور اتمیک `MASTER_ADMIN` می‌شود** (`SystemState.tryClaimMasterAdmin`، از فاز ۲). تبدیل یک
کاربر به `admin` یک عملیات جدای مدیریتی توسط `MASTER_ADMIN` است (در فاز Admin پیاده می‌شود)،
نه چیزی که کاربر خودش با OTP به آن برسد.

## ۲. سیاست OTP

مقادیر = دقیقاً همان مقادیر تست‌شده‌ی Legacy در production (نه حدس)، از طریق env قابل‌تغییر:

| پارامتر | پیش‌فرض |
|---|---|
| طول کد | ۴ رقم |
| انقضا | ۱۲۰ ثانیه |
| فاصله‌ی ارسال مجدد | ۶۰ ثانیه |
| سقف درخواست | ۵ در هر ساعت |
| سقف تلاش تأیید | ۵ بار |
| قفل پس از سقف | ۱۵ دقیقه |

کد همیشه هش‌شده (bcrypt) ذخیره می‌شود، هرگز plaintext. یک رکورد Otp فعال برای هر
(phone, purpose) — درخواست جدید رکورد قبلی را بازنویسی می‌کند.

## ۳. سیاست رمز عبور (فقط admin/master_admin)

bcrypt (rounds پیش‌فرض ۱۰، env-پذیر)، حداکثر ۵ تلاش ناموفق → قفل ۱۵ دقیقه‌ای (متقارن با OTP).
خطای عمومی یکسان برای «کاربر یافت نشد» / «نقش نامناسب» / «رمز اشتباه» تا امکان شمارش شماره یا
نقش وجود نداشته باشد. تنها استثنا: پیام صریح «هنوز رمزی تنظیم نشده» — چون این endpoint فقط
برای کارکنان داخلی است، نه عموم مردم.

## ۴. Token / Session

- **Access JWT:** ۱۵ دقیقه، شامل `sub` (userId) و `role`. نقش داخل توکن است، نه از DB در هر
  درخواست خوانده می‌شود — یعنی تغییر نقش توسط MASTER_ADMIN حداکثر تا ۱۵ دقیقه (یا تا refresh
  بعدی) طول می‌کشد تا اعمال شود؛ این یک تأخیر کوتاه است، نه حفره‌ی امنیتی، چون refresh همیشه
  کاربر را دوباره از DB می‌خواند.
- **Refresh JWT:** ۳۰ روز، **یک‌بارمصرف** (Rotation). هر refresh token یک رکورد مستقل در
  کالکشن `RefreshToken` دارد — همین کالکشن **خودش لیست نشست‌های فعال کاربر است** (نیازی به
  مدل جداگانه برای «دستگاه‌ها» نبود).
- **تشخیص سرقت (Reuse Detection):** اگر یک refresh token که قبلاً Rotate/باطل شده دوباره
  استفاده شود، این نشانه‌ی احتمال سرقت توکن است — به‌عنوان اقدام احتیاطی، **تمام نشست‌های آن
  کاربر باطل می‌شوند** و باید دوباره وارد شود.
- **تحویل:** هم‌زمان از دو مسیر — httpOnly Cookie (برای صفحات ادمین در مرورگر) و در بدنه‌ی
  پاسخ JSON (برای کلاینت موبایل/جدا). هیچ‌کدام بر دیگری اولویت معماری ندارد؛ کوکی برای انتخاب
  خودکار در refresh/logout endpointها اولویت خواندن دارد (چون مرورگر آن را خودکار می‌فرستد).

## ۵. مدیریت نشست‌ها (تصمیم تأییدشده‌ی اضافه)

- `GET /api/v1/auth/sessions` — لیست نشست‌های فعال (userAgent، ip، createdAt، expiresAt،
  isCurrent).
- `DELETE /api/v1/auth/sessions` — خروج از **همه‌ی دستگاه‌های دیگر** (نشست فعلی زنده می‌ماند).
- `DELETE /api/v1/auth/sessions/:id` — باطل‌کردن یک نشست خاص (ownership-checked).
- برای خروج کامل از جمله دستگاه فعلی: کلاینت `DELETE /sessions` را با `POST /logout` ترکیب
  می‌کند. این تفکیک عمدی است (الگوی رایج: «خروج از سایر دستگاه‌ها» جدا از «خروج از این
  دستگاه»)، نه یک محدودیت فنی.

## ۶. بازیابی رمز ادمین (تصمیم تأییدشده‌ی اضافه)

روی همان زیرساخت OTP سوار شده (purpose جدا: `password_reset`)، بدون هیچ مدل یا مکانیزم جدید:

1. `POST /password-reset/request` — **همیشه** یک پیام عمومی برمی‌گرداند، صرف‌نظر از این‌که
   شماره متعلق به یک حساب ادمین باشد یا نه. کد واقعاً فقط وقتی ارسال می‌شود که شماره متعلق
   به یک `admin`/`master_admin` فعال باشد.
2. `POST /password-reset/confirm` — کد را تأیید و رمز جدید را ست می‌کند؛ **همه‌ی نشست‌های
   موجود آن حساب باطل می‌شوند** (استاندارد امنیتی: تغییر رمز = خروج اجباری از همه‌جا).

نکته‌ی طراحی: چون مرحله‌ی ۱ فقط برای شماره‌های واجد شرط واقعاً OTP می‌سازد، اگر کسی مرحله‌ی
۲ را برای یک شماره‌ی غیر-ادمین امتحان کند، به‌طور طبیعی با خطای عمومی `OTP_NOT_REQUESTED`
مواجه می‌شود — بدون نیاز به منطق ضد-شمارش جداگانه.

| متد | مسیر | Auth | بدنه |
|---|---|---|---|
| POST | `/api/v1/auth/otp/request` | ندارد | `{phone}` |
| POST | `/api/v1/auth/otp/verify` | ندارد | `{phone, code}` |
| POST | `/api/v1/auth/login/password` | ندارد | `{phone, password}` |
| POST | `/api/v1/auth/password-reset/request` | ندارد | `{phone}` |

| GET | `/api/v1/auth/me` | Access Token | — |
| GET | `/api/v1/auth/sessions` | Access Token | — |
| DELETE | `/api/v1/auth/sessions` | Access Token | — |
| DELETE | `/api/v1/auth/sessions/:id` | Access Token | — |

## ۸. سرویس SMS

هیچ سرویس واقعی پیامک انتخاب/پیکربندی نشده (خارج از این تصمیم). طبق `MASTER-PROMPT.md` §۱۹
پشت یک interface (`SmsProvider`) پنهان شده؛ فقط پیاده‌سازی dev-only (`ConsoleSmsProvider`، کد
را در کنسول لاگ می‌کند) وجود دارد. `getEnv()` عمداً **اجرا در production با
`SMS_PROVIDER=console` را رد می‌کند** تا کد OTP هرگز در لاگ production ظاهر نشود.
**سؤال باز:** انتخاب سرویس واقعی (`sms.ir`، Kavenegar، ...) نیاز به تصمیم کاربر دارد؛ افزودن
آن فقط یک پیاده‌سازی جدید از `SmsProvider` است، بدون تغییر در `otpService`/`authService`.

## ۹. تست‌ها

- **۶۷ تست واحد** (بدون DB): مدل‌ها + `password.ts` + `jwt.ts` + `apiResponse`/`AppError`.
- **تست‌های یکپارچه‌ی واقعی نوشته شدند** (`otpService.integration.test.ts`,
  `authService.integration.test.ts`) — پوشش: ادعای MASTER_ADMIN اولین کاربر، cooldown/سقف
  ساعتی/قفل OTP، قفل رمز ادمین، rotation + reuse detection توکن، logout تک‌دستگاهی، بازیابی
  رمز + ابطال همه‌ی نشست‌ها، رفتار no-op بازیابی رمز برای غیر-ادمین.
- **اجرا نشدند** در این sandbox — همان محدودیت شبکه‌ی ثبت‌شده برای Playwright/مدل‌های Phase 2:
  دانلود باینری MongoDB از `fastdl.mongodb.org` مسدود است. تأیید شد که شکست، شکست دانلود
  باینری است، نه خطای کد. **باید در dev/CI واقعی با `npm run test:integration` اجرا و تأیید شود.**
